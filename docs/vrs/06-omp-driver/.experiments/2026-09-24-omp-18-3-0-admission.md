# omp 18.3.0 admission checks

## Question

The omp launch gate admits the `18.0` and `18.1` minor series. The managed
runtime now ships `18.3.0`; per OMP-R05, may the `18.3` series be admitted, or
did one of the delivery-critical surfaces move? The intervening `18.2` minor is
not measured by this capture and must remain refused.

Date: 2026-09-24. Binary under test:
`/nix/store/b2y6c25kq59pnwrbx3l5mbp1naz4wzbg-omp-18.3.0/bin/omp`.
`--version` printed `omp/18.3.0`. Linux x86_64, dev3. Every probe below named
that store binary explicitly.

## Method

The five OMP-R05 checks from
[`2026-08-28-omp-18-0-9-admission.md`](./2026-08-28-omp-18-0-9-admission.md)
were repeated with throwaway TypeScript extensions. Print mode used
`-p --no-session --no-tools --no-lsp --no-skills --no-rules --no-extensions`,
loaded the explicit probe with `-e`, and redirected stdin from `/dev/null`.
Interactive checks ran in isolated named PTYs. The approval check forced
`--approval-mode always-ask`. All probe output, session state, hook root,
catalog, workspace, and PTY registries lived below one newly-created
`/tmp/st2-omp1830-admission.*` root.

The delivery check used the shipped path rather than imitating the channel. The
branch's built `st2` binary installed its immutable hook set into the disposable
hook root and launched the candidate through `st2 driver omp-session`; the
injected shipped `omp-channel.ts` spawned that same `st2` as `driver
omp-channel`. The scratch catalog validated with zero errors and zero warnings.

## Result

**1. Extension load — pass.** At extension initialization the first argument
reported:

```json
{"sendUserMessage":"function","sendMessage":"function","on":"function","piNamespace":true}
```

The three calls used by the shipped channel and the `.pi` internals namespace
remain present. This is unchanged from 18.0.9 and 18.1.2.

**2. Lifecycle inventory and missing `agent_settled` — pass.** A print-mode
turn fired, in order:

```text
session_start, agent_start, turn_start,
message_start, message_end, message_start, message_end,
turn_end, agent_end, session_shutdown
```

The interactive turn fired the same order; `session_shutdown` arrived when the
probe PTY was deliberately stopped. Registering `agent_settled` did not throw
and no such event fired. A raw byte count over the candidate binary found
`agent_settled` **0** times. It found `tool_approval_requested` **5** times and
`tool_approval_resolved` **5** times; the previous 18.0.9 and 18.1.2 captures
found three copies of each approval-event string, but the observed event names
and payload behavior below did not change. OMP-R03's sampled settle remains
necessary.

**3. Idle edge — pass.** `ctx.isIdle()` was `false` at `agent_end` in both
modes. With a 25 ms sampler, the interactive run's first sample at **+26 ms**
was `true`; the print-mode run's first sample at **+34 ms** was `true`.
Interactive timing is effectively unchanged from 18.0.9 (+25 ms) and 18.1.2
(+26 ms). Print timing is close to 18.0.9 (+26 ms) and faster than the +186 ms
18.1.2 sample. The load-bearing rule is unchanged: `agent_end` itself is not an
idle proof; the channel must wait for the first positive bounded poll.

**4. Approval correlation — pass.** An interactive bash tool call under
`--approval-mode always-ask` emitted this pair and the approved command wrote
`APPROVAL_OK`:

```text
tool_approval_requested
  sessionId: 01a0d327-f97b-73f0-b753-79deec0d93d7
  toolName: bash
  toolCallId: call_3qGiZrIwTc9U7mpZdbpnI5t9|fc_0309d0d61cdae49e016ab50833382087d28df84c5a09c533fb
  approvalMode: always-ask

tool_approval_resolved
  sessionId: 01a0d327-f97b-73f0-b753-79deec0d93d7
  toolName: bash
  toolCallId: call_3qGiZrIwTc9U7mpZdbpnI5t9|fc_0309d0d61cdae49e016ab50833382087d28df84c5a09c533fb
  approved: true
```

Both `sessionId` and the complete `toolCallId` match across the pair, preserving
the OMP-R02 blocked-on-human correlation edge. This payload shape is unchanged
from 18.0.9 and 18.1.2.

**5. Shipped-driver live delivery — pass.** Before the gate edit, the built
wrapper refused the candidate without claiming the seat:

```text
Error: omp 18.3.0 is unverified (admitted minors: 18.0.x, 18.1.x); repeat the
docs/vrs/06-omp-driver admission checks before extending the gate
```

With only `18.3` added to `SUPPORTED_OMP_MINORS`, the same binary installed hook
set
`sha256-83f5c9558982ce85c094e2d769ef4eaebcf0cab7d8670702c2a9663806cfcc5e`
and launched `lab.omp1830` through `st2 driver omp-session` with PTY runtime
`omp1830-demo-run`. Presence reached `available`, and the wrapper and shipped
channel published:

```json
{"schema":"st2.harness-state.v1","agent":"lab.omp1830","harness":"omp",
 "state":"idle","blockedOn":"none","inputBuffer":"unknown","ask":"none",
 "ptySession":"omp1830-demo-run","incarnation":"616732-1790249631546-0",
 "seq":1,"transitions":1}
```

A real `st2 message send lab.omp1830 --as lab.omp1830` created
`1790249647054-vgc047.md`. The shipped channel delivered its body into the idle
TUI without screen injection: harness state moved to `active`, transitions
**2**; the model ran the requested bash command and produced the exact artifact
content `DRIVER_DELIVERY_OK`; it replied `DRIVER_DELIVERY_DONE`; and state
returned to `idle`, transitions **3**, under the same incarnation and sequence.
This is the same complete delivery behavior measured on 18.0.9 and 18.1.2.

## Conclusion

All five delivery-critical checks pass on omp 18.3.0. The extension API,
lifecycle vocabulary, still-missing `agent_settled`, sampled idle edge,
approval correlation, and shipped driver delivery loop remain valid. Admitting
the `18.3` minor series alongside `18.0` and `18.1` is justified under decision
0007-omp-is-a-fifth-native-driver-with-its-own-channel-and-a-hard-version-gate
and OMP-R05.

The gate remains per minor. This capture does not admit or make any claim about
`18.2`, and it does not assert that harness-context `tokens` arithmetic was
remeasured on 18.3.0; the exact-build fixture for that separate HC-R13/HC-T03
question remains unchanged.

## Residual risk

- The approval deny path remains unmeasured, as in the earlier captures
  (OMP-T01, DQ-OMP-1).
- This is one Linux x86_64 capture using the configured `openai-codex`
  GPT-5.6-Sol model and the approval success path; it is not a provider matrix.
- Minor-series admission intentionally lets later `18.3.x` patches launch
  without another capture. A new minor remains refused.

## VRS Impact

Extends `SUPPORTED_OMP_MINORS` in `src/omp_session.rs` from
`[(18, 0), (18, 1)]` to `[(18, 0), (18, 1), (18, 3)]`, adds `18.3.0` to the
literal admission-build test, and keeps the unmeasured `18.2` minor,
neighbouring minors, majors, ambiguous banners, and pre-releases fail-closed.
OMP-R02, OMP-R03, OMP-R05, and OMP-A01 remain satisfied; no open question is
closed by this capture.
