# omp 18.4.2 admission checks

## Question

The omp launch gate admits `18.0`, `18.1`, and `18.3`. May the managed
`18.4.2` binary admit the `18.4` series under OMP-R05? `18.2` remains
unmeasured and refused.

Date: 2026-09-29. Binary:
`/nix/store/cxylsx4nnzmdwh8kb2i5nfwv6lys4p8r-omp-18.4.2/bin/omp`;
`--version` printed `omp/18.4.2`. Linux x86_64, dev3.

## Method

Repeated the five checks from
[`2026-09-24-omp-18-3-0-admission.md`](./2026-09-24-omp-18-3-0-admission.md)
with a disposable TypeScript extension. Print invocation explicitly used
`-p --no-session --no-tools --no-lsp --no-skills --no-rules --no-extensions
-e /tmp/ompr05-1000/probe.ts 'Reply with exactly PRINT_OK' </dev/null`.
Interactive lifecycle and approval checks used separate named PTYs in the
scratch `PTY_ROOT=/tmp/ompr05-1000/pty`. Approval used
`--approval-mode always-ask`; Johannes personally selected Approve in the
isolated PTY. The same extension logged event name, timestamp, `ctx.isIdle()`,
and approval correlation fields to separate JSONL files; its `agent_end`
listener started a bounded 25 ms poll (at most 80 samples).

The real login `HOME` retained the existing provider login without copying
or modifying it. XDG configuration/state/runtime, `PTY_ROOT`, `ST_HOOKS`,
catalog, workspace, daemon socket and outputs were isolated below
`tmp/st3-adoption/omp-r05/` (short socket alias `/tmp/ompr05-1000`).
The daemon was the integration branch
`schickling-assistant/dotfiles-integration` at `e8e68762` (including the
sandbox fleet-test fix #688), built with `CARGO_BUILD_JOBS=8`. Its Nix build's
unrelated example test failed because `/bin/rm` is absent from the Nix build
sandbox; the identical source was built with `doCheck=false` for this live
probe. The integration branch's `st2` was built and used for the shipped-driver
check, temporarily adding only `(18, 4)` after first measuring refusal.
The isolated `st3 up` daemon used explicit scratch state, socket, PTY root,
client gateway and PTY binary; a private user/mount namespace bound a scratch
`/usr/bin` with `env` and `printf` for its login-shell environment probe.
No shared broker or live PTY registry was changed.

## Result

**1. Extension load — pass.** Extension initialization recorded:

```json
{"sendUserMessage":"function","sendMessage":"function","on":"function","piNamespace":true}
```

**2. Lifecycle inventory — pass.** The print-mode turn recorded, in order:

```text

message_start, message_end, message_start, message_end,
turn_end, agent_end, session_shutdown
```

The interactive turn recorded the same sequence; its `session_shutdown` fired
when its PTY was deliberately stopped. Registering `agent_settled` succeeded,
but neither mode emitted that event. No changed event name was observed.
The approval event names remained `tool_approval_requested` and
`tool_approval_resolved`.

**3. Idle edge — pass.** At `agent_end`, `ctx.isIdle()` was `false` in
both modes. The interactive 25 ms poll's first sample at **+25 ms** was
`true`. Print mode exited immediately: `session_shutdown` at **+1 ms** was
already `true`, and no 25 ms timer could run before process exit. Thus the
first observed positive print-mode edge was shutdown at +1 ms, not a poll
sample; this capture does not claim a 25 ms print-mode poll observation.
The shipped channel's bounded sampler remains necessary for interactive turns.

**4. Approval correlation — pass.** The requested harmless bash command wrote
`APPROVAL_OK` after the person approved. The emitted pair was:

The scratch catalog validated **one agent, zero errors, zero warnings**. With

## Conclusion

All five delivery-critical surfaces pass on omp 18.4.2: extension API,
lifecycle vocabulary (still no `agent_settled`), first positive sampled
interactive idle edge, approval correlation, and complete shipped-driver
message delivery. Admit minor `18.4` beside `18.0`, `18.1`, and `18.3` under
OMP-R05 and decision 0007. This does not admit `18.2` and does not change the
separate exact-build `MEASURED_CONTEXT_VERSIONS` fixture.

## Teardown and residual risk

All three scratch PTYs (`omp-r05-interactive`, `omp-r05-approval`,
`omp-r05-driver`) were killed and removed; the isolated registry printed `[]`.
The named isolated daemon was stopped and the short `/tmp/ompr05-1000` socket
alias removed. No shared daemon was restarted, and the real-home credential
profile and live PTY registry were not modified.

The approval denial path remains unmeasured. This is one Linux x86_64 capture
using configured `openai-codex/gpt-6-sol`, not a provider matrix. Print-mode
shutdown preempted the timer, so print idle timing is bounded only by the
observed +1 ms shutdown edge. Later 18.4.x patches are intentionally admitted
without a new capture; later minors remain refused.

## VRS Impact

Extends `SUPPORTED_OMP_MINORS` to `[(18, 0), (18, 1), (18, 3), (18, 4)]`
and adds exact build `18.4.2` to the literal admission-build test. OMP-R02,
OMP-R03 and OMP-R05 remain satisfied; no open question is closed.
