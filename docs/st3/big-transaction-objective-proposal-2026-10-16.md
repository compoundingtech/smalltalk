## 1. Per-member objective and breach ownership

Add a **write transaction over budget** objective per member: in each rolling one-hour window, count physical SQLite write transactions whose elapsed time from attempting `BEGIN IMMEDIATE` through finalizer and `COMMIT` or rollback is strictly greater than `B_ms`. Target: **zero** such transactions. Show `count`, `over_B_count`, `p99_ms`, `max_ms`, the exact `B_ms`, member and window. Show an in-progress transaction's elapsed time separately; do not claim it is a completed sample. Preserve the existing 1m/5m/1h windows and the existing `transaction/write` and `transaction/writer_hold` objectives. The new objective is an additional clear contract, not a replacement for the current 100 ms maximum before Nathan chooses the final budget. No 24-hour claim follows from these in-memory windows.

The current [`run_write_batch`](../../crates/smallclaims/src/sqlite.rs) starts `StoreWork::WriteTransaction` just before `BEGIN IMMEDIATE` and drops its timer just after commit/rollback (`:860`, `:977`), so its write-transaction window covers the physical batch, including savepoints, finalizers and commit. Its `WriterHold` starts before `BEGIN` and ends after post-commit observers and answers; that longer hold is useful for queue impact but is not identical to the transaction interval. The [`WriterTransaction`](../../crates/smallclaims/src/sqlite/transaction_finalizer.rs) timer starts inside `WriterTransaction::new` after the loan has begun a transaction and run prepare, so it omits that beginning. Explicit raw `Connection` transaction control and SQLite autocommit statements can also evade that managed timer. The implementation must close these source coverage gaps before claiming that it counts **every** write transaction. Audit and instrument the existing writer entry points, including direct loans in the inventory, using one shared transaction-boundary accounting path. Report uncovered or failed instrumentation as `UNKNOWN`, never zero. A conservative writer-hold guard can catch slow uninstrumented transactions in CI, but cannot stand in for a precise physical-transaction count.

For each over-budget completion, retain a bounded local breach record containing `member`, begin/end or rollback time, `held_ms`, `holder` route/task, client if known, `at` file/line, batch/lend kind and physical transaction identifier. A batch gets its full physical duration; record all jobs that participated and the longest job separately so the one charged holder is not mistaken for proof of sole causality. If a holder is `(thread tokio-rt-worker)` or `(other)`, preserve that as uncertain attribution and seek a source join before naming a fix. Do not expose sensitive request bodies. Existing holder records and windows are always on; do not enable the profiler or add a collector by default.

The breach-to-mission loop should use a durable idempotency key `(member, budget revision, holder route/task, stable site ID, episode start)`. A registered stable site ID is `crate::function` plus job kind (for example `smallclaims::store::project_replication_backlog_chunks/lend`), never file:line; keep `at` file:line as evidence because deploys move lines. For a holder/site, an episode starts with the **first completed over-`B_ms` transaction while no episode is open**, including after startup with unknown history. It ends only after a **complete rolling one-hour window** with zero over-`B_ms` transactions and known coverage of all instrumented writer entries; persist both transitions. Further samples in the open episode update its evidence. One active owning-seat fix step per **distinct** verified holder/site is opened, while restart, replay and two peers observing it cannot reopen an already recorded episode. A missing healthy window, downtime or unknown coverage leaves the episode open. Route unknown/overflow labels to a visible typed attribution block rather than assigning a speculative owner or marking the breach fixed. Bluey synchronization stays the top P0 capacity priority. The inventory's resource-observation step belongs to existing GitHub trim work; Silber's projection lend is a separate holder/site.

## 2. Fix the displayed zero without relaxing the objective

`GET /v1/client/request-latency` builds `writer-hold` with `max_ms = targets.transaction.max_ms` and no `p99_ms` in [`slo.rs`](../../crates/st3/src/slo.rs) `:319`–`:330`. [`objectives::rows`](../../crates/st3/src/objectives.rs) `:25`–`:62` has no `writer-hold` arm, so the generic branch calls `p99` with absent `p99_ms`. `p99` at `:97` uses `unwrap_or_default()`, displaying **0.0 ms** and evaluating the over-100-ms share against a fictional p99 target. The source target is not zero: [`slo/targets.toml`](../../slo/targets.toml) sets transaction `max_ms = 100`, and `st doctor` uses that maximum for `slo/writer-hold`. This is a **display and objective-selection bug**, not a real zero target.

`slo.rs:290`–`:295` already exports the same `StoreWork::WriterHold` series under `transaction.writer_hold`; the `transaction` arm in `objectives::rows` already evaluates it with `max_latency` as `transaction/writer_hold`. An extra maximum objective for the descriptive `writer-hold` row would duplicate that objective. Add an explicit `writer-hold` arm that emits **no objective row**. Keep the request-latency `writer-hold` holder table and the `st doctor` descriptive line. `st slo ls` shows only `transaction/writer_hold` for this series. `st slo explain writer-hold` and `st slo chart writer-hold` should resolve as documented aliases to `transaction/writer_hold`, naming that canonical ID in the response; the API uses the same canonical objective. Test no `p99 ≤ 0.0 ms` row, one over-100-ms hold missing `transaction/writer_hold`, and identical `ls`/`explain`/`chart` target and status. Reject missing required target fields in actual p99 objectives rather than silently converting them to zero. The new `B_ms` objective is reviewed separately; do not rewrite the existing 100 ms target while fixing display.

## 3. CI guard with an actual elapsed-duration budget

Add an opt-in test-binary guard first. For every writer connection used by the test process, record monotonic `Instant` elapsed duration of each physical write transaction, starting before begin and ending after successful commit or rollback. A shared batched outer transaction is **one** guarded transaction, irrespective of savepoint/job count. Include prepare, finalizers, commit and rollback; account for any post-commit writer loan separately as a hold. At test-binary exit, fail if **any** measured transaction is `> B_ms`. The emitted failure lists test name, stable site ID, source `at`, route/task or thread, kind, elapsed ms, `B_ms`, batch job count, outcome, attribution completeness, runner class, host load and measured writer queue wait at the event. Queue wait and load are diagnostic context, never exemptions. Avoid wall-clock timestamps for the comparison.

The guard ignores only time outside a write transaction: queue wait before writer acquisition, read transactions, a loop's time between committed chunks, and deliberately idle time after the writer has been returned. It does **not** ignore fixture setup writes, migration writes, rollback paths, direct loans, commit time, host load, or a known offender. If an existing test exceeds `B_ms`, CI names and fails that test and records a finite fix owner; it is not filtered, retried away, or waived. Run a bounded growing-data fixture for each repaired site that failed before and passes after, with semantic checks for interruption, duplicate delivery and committed frontier as applicable. An uninstrumented write path fails coverage verification rather than being counted as zero.

Promote the guard from opt-in to required **only after three consecutive exact-source runs on each runner class that the required gate uses**, under normal admission, each reporting complete entry-point coverage, zero transactions over `B_ms`, and its measured physical-transaction p99.9 and maximum. Report p99.9 against the fixed `B_ms` on the reference runner; a p99.9 over `B_ms`, any over-budget sample, or an uncovered site blocks promotion, even if load appears responsible. Review the failure-line load and queue-wait context and the named offender list before promotion; fix offenders and repeat the three-run sequence rather than adding a waiver. The duration budget is the **actual physical elapsed time** `B_ms` selected by Nathan, not the existing 50 ms soft queue admission window, 256-job limit or an arbitrary test timeout. The CI command and its runner remain the repository's normal admitted host path (`scripts/st-test --push origin` before any push); this proposal adds no special three-host profiler or SQL census. A representative guard fixture should report its wall duration and sample count with the first implementation PR, so review can judge the cost of making the guard required. Until those exact-source runs exist, CI runtime impact and a claimed millisecond maximum are **UNKNOWN**.

Coverage has an explicit denominator: **all writer entry points in the inventory's 16 source rows**, expanded to each direct loan, background loan and `.batched` call site in those rows. Register each with its stable `crate::function/job-kind` ID and prove it reaches the shared transaction-boundary recorder; report covered/registered counts, not only a percentage. A source-aware test compares production writer entry points to the register and fails if a new `connection.write`, `write_background` or `.batched` site lacks registration or if two sites reuse an ID. Test-only fixture calls are outside the production denominator but remain subject to the CI guard when run. The register can grow with source; no unlisted site is treated as covered by default.

1. Unit evidence that one physical multi-job batch is measured once across prepare, all savepoints, finalizers and commit; a failed commit and rollback are measured; an autocommit/direct-loan path is covered or visibly fails coverage.
2. Source test proving `writer-hold` emits no duplicate objective, `transaction/writer_hold` remains the maximum objective, alias lookups resolve to that canonical ID, and no absent p99 field formats as zero.
3. A before/after exact-source growing-data fixture for each distinct repaired holder with physical transaction p99/max/count over `B_ms`, plus writer-hold p99/max/count over the retained 100 ms target, per member and with precise coverage. For 24-hour per-holder history absent from the held sources, report **UNKNOWN**.
4. CI failure output enumerating all over-budget transactions and source sites without waivers; the 16-row entry-point register and source-aware new-site test are complete. Passing a fixed fixture proves only that fixture; it does not establish the fleet-wide maximum until production windows and coverage show it.
