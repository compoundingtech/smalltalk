# Writer queue physical transaction plan (rank 2)

**Source plan for Intake review before implementation is submitted.** A provisional local edit and fixture exist in the writer-inventory worktree; the fixture failed on the unmodified head (`[16]` commits observed instead of `[1..16]`) and passed on the candidate. The edit is not committed or approved. `B_ms` remains Nathan's unanswered parameter. This step limits the extra physical transaction work caused by queue coalescing. It cannot establish an absolute duration or byte cap for one job, finalizer, commit or observer.

## Contract and caller check

[`WriterConnection::batched`](../../crates/smallclaims/src/sqlite.rs) is a synchronous call: each caller blocks until its own result is committed or rejected. Today `run_write_batch` takes additional queued jobs through savepoints under one `BEGIN IMMEDIATE`, then prepares/runs finalizers, commits once, observes and answers. The 50 ms and 256-job admission limits run **between** jobs and exclude the later finalizer/commit/observer time. No caller can explicitly enroll several jobs in one all-or-nothing group. The [failure-isolation test](../../crates/st3/src/store.rs) `a_failed_batched_write_undoes_only_itself` proves the intended independent result: one job may fail or panic while another succeeds. I found no documented caller contract requiring multiple callers to commit atomically; this is a source conclusion, not proof that every concurrent use is cost-neutral.

There **is** an explicit group-commit performance expectation: `concurrent_claims_share_the_writer_s_commits` in the same file enqueues 32 claims and asserts fewer than 32 commits. The proposed physical boundary changes that behavior, transaction finalizer frequency, observer frequency, batch metrics and physical commit count. Review these as a storage/API contract change; update that test only with measured cost evidence. Each `.batched` closure retains its own atomic claim/finalizer/wake transaction. `github-store` confirmed its per-item GitHub path will use explicit `connection.write()` transactions and will not edit `sqlite.rs` or depend on `.batched` grouping ([coordination](message/bceb5569dde4ef98)).

Source search covered `.batched(` calls in `crates/smallclaims/src` and `crates/st3/src` (207 syntactic occurrences, including in-source tests), plus comments matching `same transaction`, `share.*transaction`, `commit together`, and `all.or.nothing`. The calls and the failure-isolation test identify no caller that requires **two separately queued jobs** to be atomically visible together. `Plain::append_claim` in `smallclaims/src/store/runtime.rs:277` and the st3 resource/document paths each put their atomic work inside one closure. Jobs that currently read earlier jobs' writes inside a savepoint chain will instead read them after the earlier job commits, preserving FIFO order but changing the visibility boundary; any contrary caller found in broader tests blocks this candidate.

The logical replication batch is distinct from the physical SQLite transaction. `append_claim_record_tx` in `smallclaims/src/store.rs:8803` inserts one `batches` row for a claim unless supplied a `forced_batch`, even when several `.batched` jobs share an outer transaction. `seed_replica_envelopes_signed_tx` at `:3625` seals each logical batch into an envelope. Thus the 1,000 independent-claim fixture predicts the **same** local batch and envelope count under all three queue arms, but this remains a measured assertion: record `batches`, signed `replica_envelopes`, tombstones and logical replicated payload bytes per 1,000 claims. The source does not justify equating physical commits with signed envelopes.

The production core schema in `smallclaims/src/store.rs:439` sets `journal_mode=WAL` and `synchronous=FULL`; `busy_timeout=5000` and foreign keys are also set there. On this setting a successful WAL commit can add sync cost; actual fsync calls depend on SQLite, the filesystem and host. The file-backed cost arm must use a real disk, report the PRAGMA values it read from the connection, and keep journal/checkpoint settings identical across arms. Hetz is the Linux source runner; Silber is macOS and needs its own runner for host-specific cost. Hetz numbers will not be presented as Silber measurements.

## Candidate and proof

Compare three arms on the same source workload: **A**, unmodified 50 ms/256-job shared transaction; **B**, one queued job per physical commit, retaining its savepoint error contract; **C**, an experimental bounded group. C stops admitting another job once elapsed time since attempted `BEGIN IMMEDIATE`, plus a measured reserve from the previous finalizer/COMMIT/post-commit tail, reaches an explicit experimental `G_ms`. `G_ms` is independent of the existing 50 ms admission window; evaluate 5, 10 and 20 ms as experiment points, not approved production thresholds. The reserve must use the previous measured tail, not a guessed zero; one long job or tail can still exceed `G_ms`. Only Nathan's eventual `B_ms` can activate a production numeric policy. Choose B over C only if its physical-hold improvement and full cost/replication measurements justify the extra commits; otherwise refine C. Neither arm is described as a hard `B_ms` cap.

Both candidates return to normal admission after commit, post-commit observer and answer. Keep the `StoreWork::WriteTransaction` timer from before `BEGIN IMMEDIATE` through commit/rollback, and the distinct `WriterHold` through observers and loan return. Record physical transaction count, completed begin-to-commit p99/max, hold p99/max, commit duration and throughput. Do not silently call the 50 ms admission window or one-job payload size `B_ms`.

Use a 32-job fixture with growing 4 KiB payloads queued behind a held writer and a foreground loan between two groups. The unmodified head fails the one-physical-commit-per-job assertion; B passes. For C, assert that an admitted multi-job group commits before the queued foreground loan, that no later job has run at the loan, and that multiple physical transactions occur when elapsed work exhausts `G_ms`. A file-backed variant must expose the first committed group to a separate reader before later jobs run, then close/reopen and verify the committed prefix and idempotent replay after an injected later-job error. That gives a concrete restart boundary without claiming to simulate a power failure. The in-memory C fixture passed with an experimental 10 ms admission value; the file-backed restart fixture remains open.

Run the same 1,000-claim file-backed concurrent workload on A, B and C under normal admission, with 32 producers and the same database settings. Use **five paired repetitions per runner class** for a candidate that has not already failed a gate, report each run and its median/range. Stop a rejected arm early after any paired run below the floor. The precommitted throughput gate is candidate median writes/s **at least 90% of A's median** and no paired run below **80% of A's paired writes/s**. These are implementation cost gates, not SLO waivers. A candidate failing either goes back for redesign regardless of its latency improvement. Report job count, payload/claim mix, physical commits, elapsed wall time, writes/s, transaction and writer-hold p99/max, and total/per-commit wall time from the existing commit timer. Record prepare/finalizer/observer invocation count, total and per-job wall time, and thread CPU time where the runner exposes it. A missing CPU source is `UNKNOWN`, never inferred from wall time. Report logical batches, signed envelopes, tombstones and logical replicated bytes per 1,000 claims; the benchmark fixture must keep those counts and bytes invariant apart from documented timestamp/signature encoding differences. State fsync syscall count as **UNKNOWN** unless directly measured through an approved existing source; extra physical commits are exposure only under the actual durability setting.

## Provisional real-disk results, hetz class only

The fixture used WAL, 1,000 independent claims, 32 concurrent producers, 1 KiB value payloads, and an ext4 directory rather than tmpfs. These are source experiments, not production fleet telemetry. The callback measurements snapshot before the later envelope-sealing call. On both arms, `batches=1,000`, signed `replica_envelopes=1,000`, checkpoint tombstones `=0`, and logical replicated payload bytes `=1,691,055` per 1,000 claims. This confirms that, for this fixture, physical commit count does not control logical envelope count or byte volume. One fixture run is not an hourly fleet rate; hourly logical bytes remain UNKNOWN.

The unmodified WAL/NORMAL queue made 32 physical commits per 1,000 jobs in each baseline run, with begin-to-commit maxima of 40.4 and 42.5 ms. Under NORMAL the one-job arm called each prepare, finalizer and observer 1,000 times, versus 32 times for the baseline. Its measured callback wall totals were 7.2–9.4 ms prepare, 10.4–11.8 ms finalizer and 9.4–10.1 ms observer; baseline totals were 0.45–0.50, 0.33–0.39 and 0.41–0.47 ms respectively. Linux thread CPU was measured for each callback; fsync syscall count remains UNKNOWN. FULL is the production setting; NORMAL here is a test-only comparison and would be a separate durability contract change. Silber measurements remain UNKNOWN.

The one-job NORMAL arm and 20 ms FULL arm are rejected under the prewritten paired throughput floor; the one-job FULL arm also has an unambiguous collapse in adjacent runs. The provisional 20 ms NORMAL arm does not justify a production change: this workload has not shown a physical-hold maximum reduction, the actual production mode is FULL, and no source-joined rank-2 breach cohort has been supplied. A single job, finalizer or observer overrun remains a separate inventory site rather than evidence that grouping caused it.

Additional single-run exploratory points under WAL/FULL were `G_ms=30`: 49 commits, 598.5 writes/s, 210.0 ms physical maximum; `G_ms=40`: 33 commits, 1,199 writes/s, 50.5 ms physical maximum; and `G_ms=50`: 32 commits, 1,100 writes/s, 50.8 ms physical maximum. The 30 ms run demonstrates that a between-job admission bound does not cap a long job or commit tail. The 40 and 50 ms arms behave much like the original queue in this workload. These are findings, not proposed production thresholds.

**Disposition after Intake evidence review:** investigated, **not fixed**; no production candidate from rank 2 on today's data. The unmodified queue measured roughly 40–49 ms physical maxima in this fixture, below the current 100 ms objective, while the inventory's measured multi-second tails name the projection lend, resource-observation batch and document write.
