# Terminal agent retirement

`st agents retire agent/example/worker --as person/avery --reason "Work finished" --idempotency-key retirement-example-001` permanently retires an identity at its declaring host. The client-v0 `agent.retire` action takes `agent` and a nonempty `reason`, and requires the selected desired claim ID in `fence.runtime_desired_revision`. An optional `runtime_incarnation` fences a selected process. Exact retries retain the same key and parameters. Retirement is owner-authoritative; an unknown declaration or a request at another host is refused.

The durable `agent.retired` claim lives on the agent subject. It records the reason, actor, declaring host and declaration claim. Optional `successor` and `transfer` fields reserve compatibility for later custody work; this slice does not set them. `agent.retire` is the production writer. Runtime selection gives this terminal evidence precedence over every declaration, including a later replicated declaration, mission materialization and replay. A retired name cannot be declared again. History presents its state as `retired`; runtime selection stops its process. Stop, suspend and delivery hold remain independent and reversible. The existing stui runtime action is labeled Stop because it invokes reversible stop; terminal retirement is created through the CLI or client action. Retired rows expose only history/navigation actions.

Every first locally produced `message.sent` checks lifecycle inside the serialized writer transaction, after the operation's previous-result and changed-body checks. HTTP `/v1/messages`, client-v0 `message.send`, the CLI, adapters using those APIs and daemon producers using the common transaction primitive share admission. A send committed before retirement succeeds; one ordered after retirement is refused. The 409 error has `code: "recipient-retired"`, `applied: "none"` at the envelope and in `details`, and `details.refusal: { "variant": "Retired", "recipient": "agent/example/worker" }`. The CLI exits nonzero and names the recipient and variant. No message, operation receipt or retry item is created for a refusal.

Exact retries of accepted sends return the original receipt after retirement. Changing an accepted request under its key retains the idempotency mismatch error. A lost transport reply remains unconfirmed: retirement cannot turn a potentially accepted send into a confirmed refusal. Replicated sends are accepted history, so import and replay do not perform first-send admission.

## Replication and rollout

Upgrade fleet members together before enabling retirement. The action checks the configured peers and active fleet member incarnations against their last advertised registry digests. It returns `retirement-upgrade-required` with `applied: "none"` until every such peer advertises this build's registry. The gate requires exact digest equality, including after any later registry change: retirement refuses again until all configured/active members match that registry. A host removed from the membership and configuration is outside that gate; an offline member with no matching advertisement keeps retirement disabled. Operators must prevent downgrading a member after it advertises the new registry and upgrade new members before admitting them to a fleet with retired identities. This advertisement guard complements coordinated rollout; it cannot prove the currently running software of an unreachable member. A downgraded or rejoining old binary continues to operate without enforcing retirement; this slice has no mechanism to block that binary.

The registry and retention rules digests change. The current main baseline uses core storage version 19 and checkpoint rules version 15; retirement adds no further storage or checkpoint version change. These numbers do not imply matching registry or retention rules. Startup adds partial indexes over retained unknown/invalid lifecycle records and per-subject lifecycle operation identities, plus keyed runtime-selection triggers. Send admission probes only the recipient’s lifecycle rows, including when unrelated operation conflicts exist. Projections remain rebuildable from the durable terminal claim. Older registries preserve an unfamiliar kind as retryable `UnknownKind` (`unknown-claim-kind`); a known kind with an unfamiliar field is `UnknownField` (`unknown-claim-field`). Both retain the original raw claim and admit that same claim after upgrade. An old member cannot enforce a kind it does not recognize, which is why retirement creation is gated. Older client decoders treat unfamiliar error codes as generic errors and preserve the message and details.

First installation of the claims index was measured on this host with the daemon's bundled SQLite 3.46.0 and a synthetic 1,000,510-claim, 1.947 GB table: 0.7–1.1 seconds warm, 4.1 seconds after per-file cache discard, with a 1.18 MB index. For **ten million claims with the same row sizes and kind/operation mix on the same disk**, a rough linear estimate is **10 seconds warm / 40 seconds cold** for that index build. This is a conditional estimate, not a measured restart time for the approximately 19 GB live database: total database bytes do not establish its claim count, and startup also builds the retained-record index and initializes projections. Whole-store downtime remains unknown. intent.desired insertion adds 11 VM steps without an operation ID, or 17 with one, in the matching-engine probe. Evidence: `doc/fleet/smalltalk/agent-retirement/bundled-sqlite-index-and-intent-cost@ba17fc0b703986f9769bd8d5981dfbfbab2887488cbfe0a25753f1ed2c605aea`.

A host refuses a fresh send once **its own graph** contains retirement. The owner has an exact writer fence. Other hosts continue normal inbox delivery while the owner is offline and before retirement replicates. Missing declarations alone do not cause a refusal. Locally retained unknown/invalid lifecycle records, conflicting lifecycle operations or a retirement with incomplete/conflicting declaration evidence produce `LifecycleUnavailable` with `applied: "none"`; an unreachable owner alone does not.

An early send accepted on another host before retirement replicates remains durable history and may reach the retired inbox later. Resolving that custody race, moving unfinished mail, selecting successors, Unknown/Suspended refusals and fencing `/v1/messages/{id}/claims` are deferred from issue #2351. No automatic custody transfer is introduced here.
